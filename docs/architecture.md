# Architecture

## Context

CareBridge is an internal console for a care-coordination team. Clinicians review their
patient panel and document encounters. Administrators manage staff accounts. Auditors need
read-only access to clinical records and a trustworthy activity history.

The application is deliberately small: one Next.js deployment and one PostgreSQL database.
There are no queues, background workers, or client-side data stores in the current release.
That keeps the operational surface manageable while the product is still finding its shape.

## System context

```text
Clinician / Admin / Auditor
            |
            v
   Next.js App Router
   - server components
   - server actions
   - route handlers
            |
      +-----+----------------------+
      |                            |
      v                            v
 PostgreSQL (Prisma)        Amazon Bedrock
 users, sessions,           (optional; mock
 patients, encounters,       provider locally)
 audit events
            |
            v
   Structured logs (stdout)
```

The browser never receives a database credential, an AWS credential, or a model prompt.
Server components render data after resolving the session and permission checks.

## Request paths

### Page request

1. Middleware checks for the presence of the session cookie and redirects anonymous
   requests to the sign-in page. This is a fast-path filter, not the authorization decision.
2. The `(app)` layout calls `requireSession`, which loads the session and active user from
   PostgreSQL. Invalid, expired, or revoked sessions are cleared.
3. The page applies a permission check. Unauthorized roles receive a not-found response for
   administrative screens, which avoids advertising those routes.
4. Services query Prisma and return only the fields the page needs.

### Mutation request

Mutations use server actions or route handlers, never client-side database access. Each one:

1. Resolves the session.
2. Applies the same permission helper used by the UI.
3. Parses input with Zod.
4. Performs the database change.
5. Writes an audit event when clinical or account state changed.
6. Revalidates the affected paths.

### Summary request

`POST /api/encounters/:id/summarize` is a route handler because it needs a JSON response for
the client form. It verifies the origin header and Fetch Metadata before accepting the
request, re-checks that a clinician owns the encounter, and delegates to the summary
workflow. The workflow audits both blocked attempts and successful generations.

## Data model

| Model | Purpose | Notable indexes |
| --- | --- | --- |
| `User` | Staff identity, role, activation state, password hash | unique email |
| `Session` | Server-side session with digest, expiry, revocation | unique digest, user + revoked, expiry |
| `Patient` | Demographics, record number, status, primary clinician | unique record number, name, status |
| `Encounter` | Clinical note, timestamp, optional generated summary | patient + time, clinician |
| `AuditEvent` | Structured activity record with hash chain | time, actor + time, resource, action + time |

Identifiers are CUID strings generated by Prisma. Timestamps are stored as `TIMESTAMP(3)`
and rendered in UTC to keep server and client output consistent.

Deletes are limited. Patient encounters cascade when a patient is removed, but encounters
restrict deletion of a clinician. In practice, accounts are deactivated rather than deleted
so historical audit references remain meaningful.

## Authentication

Passwords are hashed with bcrypt cost 12. The login action applies a fixed-window limiter
keyed by client address before verifying the password, then writes an audit event for the
outcome. Successful sign-in creates a 32-byte random session value, stores its SHA-256
digest, and sets the value in a cookie. The cookie is HTTP-only, same-site `lax`, and
`secure` outside development.

Sessions are database rows with an eight-hour lifetime. Sign-out revokes the row and clears
the cookie. A request for a revoked, expired, or inactive account does not receive a user.

## Authorization

`src/lib/auth/rbac.ts` is the single permission matrix. Roles are `ADMIN`, `CLINICIAN`, and
`AUDITOR`. Permissions are named after capabilities, not screens:

- `dashboard:read`
- `patient:read`
- `patient:write`
- `note:summarize`
- `user:manage`
- `audit:read`

Pages call `can` and render not-found when the role lacks access. Server actions call
`requirePermission`, which throws a `ForbiddenError`. Navigation visibility is derived from
the same matrix, so a role never sees a link it cannot use.

## Audit chain

Audit events are written in the same transaction as the change they describe. The writer
reads the most recent event hash, constructs a canonical object with sorted keys, hashes it
with SHA-256, and inserts a row containing the previous hash and the new hash.

Verification fetches a window in descending order, reverses it, and checks:

- the first event's previous hash is null or outside the window;
- each subsequent previous hash equals the prior event hash;
- each event's recomputed hash equals its stored hash.

A break is reported with the index and timestamp. The scheme is tamper-evident within the
retained window. A database operator who can rewrite every row can also rebuild the chain,
so serious deployments should export audit events to append-only storage and restrict
database access.

## LLM boundary

The provider interface accepts a system prompt, a user prompt, and small inference settings.
`summarizeEncounterNote` owns the policy:

- high-severity injection signals block the request;
- identifiers are redacted before the provider call;
- the response must be between 40 and 2,000 characters;
- the response must not contain assistant disclaimers or identifiers;
- the response must not be longer than the source note.

The Bedrock provider uses the Converse API with a 512-token cap, low temperature, and a model
identifier from the environment. The mock provider extracts the first sentences of the note
and applies the same redaction, which makes local behavior predictable and keeps tests
offline.

## Failure behavior

| Failure | Behavior |
| --- | --- |
| Database unavailable | Health endpoint returns 503; pages surface the framework error boundary |
| Invalid credentials | Generic sign-in error; denied audit event |
| Rate limit exceeded | Sign-in rejected with retry information; rate-limit audit event |
| Model unavailable | Summary request returns 502; error audit event with model and duration |
| Guardrail block | Summary request returns 422 with a reason; denied audit event |
| Audit chain broken | Admin screen shows the first broken position in red |

## Deployment shape

The application is a stateless Next.js server and can run on ECS Fargate behind an
application load balancer. PostgreSQL belongs in RDS with automated backups and private
networking. Secrets should come from Secrets Manager rather than task-definition plaintext.
Logs go to stdout and are collected by the platform log driver; Bedrock calls use a task
role scoped to the configured model.

The repository does not ship Terraform. Teams adopting it should add their own
infrastructure definitions and treat the description above as a starting point.
